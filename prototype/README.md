# Prelim State Packet Prep (prototype)

Next.js app that runs entirely in the browser (no backend):

- **pdf.js** (`pdfjs-dist`) shows the PDFs and reads their text/positions
- **pdf-lib** splits/merges pages, replaces text, adds text, deletes pages

```bash
npm install
npm run dev        # http://localhost:3100  (npm run dev -- -p 3100)
```

Use the "Load a sample job" dropdown (3 fictional packets in `public/samples`, generated by
`../test-data/generate_test_data.py`) or drop your own PDFs.

## Flow
1. **Upload** raw PDFs (+ optional Salesforce `.json`). Files are classified by content.
2. **Process**: finds the ADI pages, splits the 50-page contract (agreement / cancellation notice /
   disclosure / DocuSign certificate), swaps the outdated emails, fills missing signature dates,
   builds the 5 documents (+ a name-clarification letter when the e-bill name differs).
3. **Review**: checks (DC size, panel count, audit date, DocuSign ID, names, e-bill account/meter,
   Chatter notes), portal values with copy buttons, and the processed documents (viewable/editable).

## Demo mode
Sample jobs read their checks, portal values and array table from `public/samples/<job>/demo.json`
(built by `../test-data/build_demo_json.py`), so the demo is deterministic. The PDFs are still built
live by the pipeline; if that ever fails, the golden PDFs in `samples/<job>/expected/` are shown.
Files you upload yourself always go through the real pipeline.

## Prototype shortcuts (be upfront with the client)
- E-bill values come from a text layer embedded in the sample PDFs. **Real bill photos need OCR.**
- "Replace text" covers the old text with a white box and draws new text (pdf-lib cannot rewrite
  text in place). Fine for a demo, not a production editor.
- Rules (emails, license expiry, page markers) are tuned to the sample documents.

Code: `lib/process.ts` (the pipeline), `lib/edit.ts` (PDF edits), `components/` (UI).
